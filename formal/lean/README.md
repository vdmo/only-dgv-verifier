# Lean 4 proofs for the quorum decision core

`OnlyQuorumCore.lean` is generated by Charon + Aeneas from `native/only-quorum-core`
(regenerate it after any change to that crate; the proofs break if behaviour changes).

| File | What is proved (any N, any quorum size) |
|---|---|
| `Proofs.lean` | `decide_no_reachable_rev`: never fails; `ConfirmedClean` ⇒ no revocation seen and `q ≤ 1 + #Clean`. |
| `Refinement.lean` | `decide_spec`: exact output of the Rust `decide` (Revoked / ConfirmedClean / PartitionFailure), incl. exact saturating tally. |
| `TlaBridge.lean` | `decide_refines_tla`: with the votes a gate collects, `decide` = ConfirmedClean ⇔ TLA `QuorumSaysClean`, = Revoked ⇔ TLA `QuorumSaysRevoked`, for any node set. |
| `TlaSystem.lean` | TLA+ `DgvQuorum` transition system (all 7 actions) and `tla_safety_all_N`: ExecutedImpliesToken, ExecHadCleanQuorum and NoReachableRevAtExec hold in every reachable state; `execution_is_reachable` rules out vacuity. |

Build: `lake build` (needs Lean from `lean-toolchain`, Mathlib, and the Aeneas Lean backend — edit the
path in `lakefile.lean`). Only the standard axioms propext / Classical.choice / Quot.sound are used.

## Not covered
Crypto (Ed25519, SHA-256), signature/nonce/freshness/key checks in `dgv-gate`, storage atomicity, networking,
gossip/anti-entropy liveness (`Convergence`), the documented partition boundary (`NoRevAnywhereAtExec` fails
by design), and properties the TLA+ model does not define (NoDualExecution, epochs, delegation).
The proofs cover the extracted tally function and the abstract TLA+ system; that the gate's `main.rs`
feeds `decide` faithful votes is an assumption.

## Delegation core (`only-delegation-core`)

`native/only-delegation-core` is the pure depth/expiry decision logic of `/delegate`
(used by `dgv-gate`); `OnlyDelegationCore.lean` is its Aeneas translation and
`DelegationProofs.lean` proves, for all i64 inputs:

- `child_depth_spec`: never errors (no overflow, even at `i64::MAX`); returns `some d` exactly
  when `parent < max`, with `d = parent + 1 ≤ max`.
- `child_expiry_spec`: an accepted child expiry is `≤` the parent's and `> now`; defaults to the parent's.
- `parent_live_spec`.
- `dchain_bound`: any chain of n ≥ 1 delegations ends at depth start+n and never exceeds the maximum.

Behaviour change vs. before: `parent.delegation_depth + 1` could overflow at `i64::MAX`
(panic in debug, wrap in release); the core compares first, so it fails closed.

**Not proved:** ancestor revocation, delegator signature checks and storage are outside the proofs.
`json_subset` is covered by a MODEL only (next section).

## Scope narrowing: `JsonSubsetModel.lean` (a MODEL, not the Rust)

`json_subset` in `native/dgv-gate/src/main.rs` runs on `serde_json::Value`, which Aeneas cannot
extract. `JsonSubsetModel.lean` is a **hand-written Lean model** of it. Nothing proves the Rust
matches the model; the link is only that they were written to the same rules and that the Rust
unit tests and e2e delegation suites exercise the Rust.

Link to the Rust: `native/dgv-gate/src/main.rs` module `json_subset_model_diff` is a differential
test (60k random + derived pairs, ~7 s) comparing the gate's `json_subset` with a line-by-line Rust
transcription of the model's `subN`, and checking transitivity on the real function. It checks
agreement on random inputs, not equality; a deliberate mutation of `json_subset` (array `any` to `all`)
makes it fail. Generated numbers include `1` and `1.0`; strings include `*`.

Proved about the model: `jsub_refl`, `jsub_trans`, and `chain_within_root` (in a chain of
narrowing steps every descendant's scope is a subset of the root's, however many hops), plus two
non-vacuity checks (`extra_key_rejected`, `changed_scalar_rejected`).

Modelling choices: numbers are `Int` (the Rust compares serde numbers exactly); object keys are
assumed unique (true for serde_json's `Map`); the relation uses fuel because Lean rejects the
direct nested-inductive form. Axioms used: standard only, no `sorry`.
